# Agent 1 — interface and navigation research

Reviewed on 2026-11-04. **15 distinct website domains** were successfully read. These are design inputs, not copied layouts. Source ages vary; findings were checked against the live documents rather than assumed to be new in 2026.

1. **discord.com** — [Appearance settings](https://support.discord.com/hc/en-us/articles/207260127-How-to-Change-Discord-Color-Themes-and-Customize-Appearance-Settings). Theme and density are user preferences, with a system-following option. **Applied:** navigation and account screens use shared theme tokens so Midnight, Dim, Daylight, and System remain coherent with the profile settings built by Agent 3.
2. **linear.app** — [How we redesigned the Linear UI](https://linear.app/now/how-we-redesigned-the-linear-ui). A cohesive UI needs hierarchy and environment testing across compact and spacious configurations. **Applied:** a labeled desktop sidebar, compact tablet rail, and mobile navigation have explicit layout breakpoints and matching content offsets.
3. **vercel.com** — [Geist colors](https://vercel.com/geist/colors). Neutral UI colors carry most structure; borders should be drawn once. **Applied:** one subtle boundary separates navigation from content; cards use neutral layers with a small cyan action accent and no stacked neon borders.
4. **primer.style** — [Accessibility fundamentals](https://primer.style/accessibility/foundations/accessibility-fundamentals/). Keyboard access, visible focus, and resizing belong to the basic interaction model. **Applied:** semantic links/buttons, visible focus rings, native form controls, and no hover-only navigation.
5. **shopify.dev** — [Polaris references](https://shopify.dev/docs/api/polaris). Unified UI components create consistency across different surfaces. **Applied:** login and registration share field, button, feedback, and panel styles; the app shell keeps one navigation language across feature screens. The old Polaris color URL redirected to this current reference and is not counted as a second site.
6. **atlassian.design** — [Color foundations](https://atlassian.design/foundations/color). Roles expressed as tokens allow light and dark modes to use appropriate neutral ramps. **Applied:** page, surface, text, muted text, border, and accent roles use the shared CSS variables rather than independent hard-coded page palettes.
7. **adobe.com** — [Spectrum colors](https://spectrum.adobe.com/page/color-system/). Purposeful color establishes hierarchy while unnecessary color dilutes important states. **Applied:** primary actions and selected navigation use cyan; errors have explicit text and a separate semantic error color.
8. **microsoft.design** — [Fluent 2 color](https://fluent2.microsoft.design/color). Lighter neutral surfaces establish hierarchy, and semantic colors should communicate meaning. **Applied:** selected links use a raised neutral surface plus icon/text indicators; no decorative fake online or unread counters.
9. **service.gov.uk** — [GOV.UK colour](https://design-system.service.gov.uk/styles/colour/). Functional colors should be assigned for predictable purposes and text contrast needs verification. **Applied:** focus, error, muted, and primary-action roles are consistent; contrast ratios were calculated for shell text and actions across the three explicit themes.
10. **carbondesignsystem.com** — [Carbon color foundations](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview). Dark layers become lighter as elevation increases, and role-based tokens preserve meaning across themes. **Applied:** main background, cards, and selected states form a restrained depth progression rather than adding large shadows to dark cards.
11. **w3.org** — [Understanding Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html). Keyboard users need to identify the currently focused interactive element. **Applied:** global `:focus-visible` outlines, including navigation and buttons, remain visible and are not removed by the form styling.
12. **mozilla.org** — [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion). A device preference can request reduced nonessential motion. **Applied:** the base stylesheet now respects this media query in addition to the account-specific reduced-motion setting.
13. **web.dev** — [Color and contrast accessibility](https://web.dev/articles/color-and-contrast-accessibility). Low contrast makes interface text harder to read; normal text needs sufficient foreground/background separation. **Applied:** primary and muted shell text were checked against page/surface colors; no thin gray-on-gray form labels.
14. **nngroup.com** — [Dark mode research](https://www.nngroup.com/articles/dark-mode-users-issues/). User preference, legibility, and clear layering matter more than assuming dark mode inherently improves every task. **Applied:** themes remain selectable; moderate font weights, visible boundaries, and a legible brand mark work in both light and dark settings.
15. **a11yproject.com** — [Accessibility checklist](https://www.a11yproject.com/checklist/). Skip links, proper headings, form labels, and semantic controls support access. **Applied:** added a visible-on-focus skip link, real labeled username/password fields, inline error/status feedback, and pending-state indicators for account forms.

## Additional implementation decisions

- Invite links retain their intended destination through login and registration. Redirects are restricted to relative local paths.
- Profile/avatar changes propagate to the sidebar through the shared profile event; sign-out clears the active identity and resets appearance.
- Mobile navigation stays separate from scrolling page content and allows safe-area space at the bottom.
- Existing post and bookmark screens receive scoped visual refinements without changing their feature behavior.

## Access limits

The X help URL and Material 3 dark-color URL could not be fetched. Apple’s page returned a JavaScript shell and its Markdown response was unsupported by the web tool. **Those three sites are excluded from the 15-site count.**

# Round 2 — topic search and pixel loading companion

Reviewed on 2026-11-04. The following **15 distinct website domains** were read for this mission. This is an additional 15-site research pass; several sites overlap with the previous mission. The Vimeo page returned only a tracking iframe, so it is not included.

1. **daily.dev** — [Search](https://docs.daily.dev/search/). Search groups relevant results by type and supports topic/source discovery. **Applied:** one topic query searches news and videos, while result groups retain clear headings and source labels. Its documentation says its previous AI search was retired; this implementation does not pretend to reproduce that retired feature.
2. **google.com** — [YouTube search.list](https://developers.google.com/youtube/data/reference/rest/v3/search/list). `q` is the topic query; video-only searches can request embeddable results. **Applied:** optional official API requests use `type=video`, `videoEmbeddable=true`, moderate safe search, and eight results. API credentials stay on the server.
3. **mozilla.org** — [AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController). Controllers cancel asynchronous fetch operations. **Applied:** a new topic search aborts the preceding search; unmount and the visible Cancel button abort requests too.
4. **nodejs.org** — [Global fetch and AbortSignal](https://nodejs.org/api/globals.html#fetch). Native fetch supports bounded HTTP requests and abort signals. **Applied:** no new HTTP dependency; provider calls have timeouts and streamed response-size limits.
5. **react.dev** — [useEffect](https://react.dev/reference/react/useEffect). Cleanup and ignoring outdated results avoid race conditions when requests resolve in a different order. **Applied:** search generation checks prevent an older query from overwriting the current topic; callbacks use fresh references.
6. **expressjs.com** — [Express 5 API](https://expressjs.com/en/api/). Explicit routes receive request input and return controlled responses. **Applied:** `/video-search` accepts only a bounded string topic, returns safe JSON, and has a small per-client rate limit. It never accepts an arbitrary provider URL.
7. **web.dev** — [High-performance CSS animation](https://web.dev/articles/animations-guide). Transform and opacity are preferable to layout-triggering animation properties. **Applied:** the small original pixel companion bobs using transform; its shadow scales rather than animating width/position.
8. **w3.org** — [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html). Important updates should be announced without taking focus. **Applied:** search progress and unavailable/empty results use status semantics; errors use an alert, with no focus stealing.
9. **algolia.com** — [Relevance overview](https://www.algolia.com/doc/guides/managing-results/relevance-overview). Useful search requires matching the query and ordering relevant results. **Applied:** the topic is forwarded unchanged to the video provider, result order is preserved, duplicates/ads are excluded, and generic demo videos never replace topic results.
10. **meilisearch.com** — [Relevancy](https://www.meilisearch.com/docs/capabilities/full_text_search/relevancy/relevancy). Relevance means returned items are appropriate for the requested query. **Applied:** cache entries are keyed by normalized topic; tests check Redis and animation return different topic-relevant videos.
11. **elastic.co** — [Match query](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query). Full-text search analyzes the supplied query instead of treating every record as a match. **Applied:** topic input is normalized and bounded before searching, and the search UI always identifies the active query rather than silently showing the general feed.
12. **opensearch.org** — [Customizing search results](https://docs.opensearch.org/latest/search-plugins/searching-data/index/). Search interfaces can choose which fields/results are returned and how those results are presented. **Applied:** video responses contain only validated ID, title, channel, canonical URL, thumbnail, duration, and publication label; raw provider objects are not passed to the browser.
13. **nngroup.com** — [Progress indicators](https://www.nngroup.com/articles/progress-indicators/). Feedback helps users understand that a slow request is still working. **Applied:** a compact pixel-search status appears during requests, has a Cancel button, and clears on success, partial failure, timeout, or cancellation; no invented completion percentage.
14. **a11yproject.com** — [Vestibular disorders](https://www.a11yproject.com/posts/understanding-vestibular-disorders/). Motion can cause discomfort, so decorative animation needs restraint and alternatives. **Applied:** the pixel animation is small, avoids large-screen movement, and stops for device or account reduced-motion preferences.
15. **chrome.com** — [Abortable fetch](https://developer.chrome.com/blog/abortable-fetch/). A single signal can cancel multiple coordinated fetch operations. **Applied:** both news and video requests share the search's cancellation signal, while `Promise.allSettled` permits useful partial results.

## Provider behavior and operational limits

- With `YOUTUBE_API_KEY` or `GOOGLE_YOUTUBE_API_KEY` in the backend environment, the official YouTube Data API is tried first.
- Without a key, the server reads public YouTube search-result data for the exact topic. It parses JSON only, never executes remote scripts, validates every video ID, rejects oversized responses, and caches successful topic results for 15 minutes.
- Public-page formats and provider access may change. If the provider is blocked or cannot be parsed, the app returns an explicit unavailable state and a direct YouTube search link. It does not fabricate video IDs or substitute unrelated samples.
- Native network checks in this environment returned eight real Redis results and eight different animation results. Examples included Fireship's “Redis in 100 Seconds” (`G1rOthIU-uo`) and TheOdd1sOut's “Animation Before Computers” (`6ecTO22ulRM`). These IDs were read from actual provider responses, not seeded into the feature.
- Search results load independently: videos can appear as soon as their provider returns even while news is still loading. Failed news does not discard successful video results, and failed video search does not discard news.

# Multilingual news follow-up

- [MDN Intl.Locale](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Locale): used native BCP47 validation and canonicalization for both common choices and custom language tags.
- [W3C language tags](https://www.w3.org/International/articles/language-tags/): preserved language/script/region metadata and per-card `lang`; a regional routing preference does not imply translation.
- [Ynet publisher RSS](https://www.ynet.co.il/Integration/StoryRss2.xml): live XML fetch returned HTTP200 and 30 Hebrew items. Hebrew topic RSS for `טכנולוגיה` returned 100 Hebrew headlines, including TheMarker, Globes, and mako.
- Auto detection covers Hebrew, Arabic/Persian/Urdu, Cyrillic, Japanese, Korean, Chinese, Devanagari and several other scripts. Ambiguous Latin text uses the selected language or the default English edition; users can choose any valid BCP47 code.
- Languages without a configured Google News edition are explicitly labeled as a worldwide fallback that may include other languages. Publisher text is preserved, never translated or presented as a supported dedicated edition when it is not.
